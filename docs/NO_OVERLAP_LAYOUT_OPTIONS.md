# بدائل تخطيط لا تتداخل لمحرر «بيان»

## لماذا لا يكفي تغيير الألوان؟

التداخل ليس مشكلة لون أو حجم زر فقط. السبب البنيوي هو جمع ترويسة وشريط أدوات ومنطقة تقسيم ولوحة مراحل ومخرجات متعددة في مساحة واحدة، ثم ترك عناصر داخلية تتنافس على المساحة. البدائل التالية تغير **بنية الشاشة** لا شكلها فقط.

> قاعدة التنفيذ في كل البدائل: تستخدم النافذة حاوية رئيسية واحدة من `TableLayoutPanel`، وكل خلية رئيسية تستضيف عنصراً واحداً فقط. لا يوضع عنصران `Dock = Fill` أو `Dock = Top` في الحاوية نفسها من دون صف أو عمود صريح. لذلك لا يمكن أن يغطي عنصر عنصراً آخر.

## التصميم 1 — Studio Canvas

هذا التصميم يشبه محرراً حديثاً بسيطاً. لا توجد مساحة نتائج بجوار الكود إطلاقاً؛ توجد **لوحة محتوى واحدة كبيرة** تتغير بين «المصدر» و«النتيجة المختارة». تبقى الأوامر والمراحل في شريط جانبي ثابت، أما المحتوى فيظهر كاملاً في الوسط.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ بيان | ملف جديد | فتح .bayan | حفظ | تحليل وترجمة | الحالة           │
├───────────────────┬──────────────────────────────────────────────────┤
│ المصدر            │                                                  │
│ Tokens / AST      │         لوحة واحدة كبيرة                         │
│ جدول LL(1)        │     كود المصدر أو artifact واحد فقط             │
│ التتبع            │                                                  │
│ الشجرة            │                                                  │
│ الرموز            │                                                  │
│ TAC / IR          │                                                  │
│ MIPS              │                                                  │
│ الأخطاء           │                                                  │
└───────────────────┴──────────────────────────────────────────────────┘
```

| البند | القرار |
| --- | --- |
| النتيجة مقابل الكود | لا يظهران معاً؛ ينقر الطالب «المصدر» أو مرحلة واحدة. |
| العناصر الثابتة | صف علوي واحد بارتفاع 52، وشريط مراحل بعرض ثابت 180. |
| التداخل | مستحيل عملياً لأن الوسط يحتوي `Control` واحداً فقط في كل لحظة. |
| الانطباع | نظيف جداً، قريب من أدوات التصميم الحديثة. |

يناسب هذا التصميم إذا أردت أن يبدو المحرر **هادئاً وبسيطاً**، ولا تحتاج مشاهدة MIPS والكود معاً دائماً.

## التصميم 2 — Compiler Journey

هذا ليس محرراً بتبويبات، بل رحلة ترجمة متسلسلة. في البداية يظهر الكود وحده. بعد الضغط على «تحليل وترجمة»، تنتقل النتيجة إلى مرحلة المرحلة، وكل صفحة تحتوي عنواناً واضحاً ومحتوى واحداً وزرين «السابق» و«التالي».

```text
┌──────────────────────────────────────────────────────────────────────┐
│ بيان — برنامج جديد | فتح | حفظ                         [ترجمة]      │
├──────────────────────────────────────────────────────────────────────┤
│  01 المصدر  ───  02 Tokens  ───  03 LL(1)  ───  04 الشجرة ...       │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│                    عنوان المرحلة الحالية                             │
│                                                                      │
│                    محتوى المرحلة فقط                                │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                      السابق              التالي                      │
└──────────────────────────────────────────────────────────────────────┘
```

| البند | القرار |
| --- | --- |
| النتيجة مقابل الكود | صفحة المصدر مستقلة، وكل artifact له صفحة مستقلة. |
| العناصر الثابتة | صف الأوامر، صف مراحل، مساحة محتوى، صف تنقل. أربعة صفوف فقط. |
| التداخل | لا توجد أعمدة أو تبويبات داخلية متزاحمة؛ كل مرحلة تملأ صفها وحدها. |
| الانطباع | أفضل تصميم للمناقشة؛ يشرح كيف يصل المصدر إلى MIPS خطوة بخطوة. |

هذا هو **الخيار الذي أوصي به** لأن مشروعكم مقرر بناء مترجمات، ولأن ترتيب المراحل أهم من تقليد شكل IDE تقليدي.

## التصميم 3 — Split-Free Notebook

هذا التصميم يعتمد صفحات كدفتر أكاديمي. يوجد شريط علوي صغير فقط، وتحته بطاقات كبيرة متساوية المساحة. كل بطاقة تمثل صفحة مستقلة: «المصدر»، «نتائج التحليل»، «MIPS»، و«التشخيصات». لا توجد لوحة جانبية دائمة ولا تقسيم عمودي.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ بيان                                             فتح | حفظ | ترجمة  │
├──────────────────────────────────────────────────────────────────────┤
│ [ المصدر ]  [ التحليل ]  [ Parse Tree ]  [ TAC ]  [ MIPS ] [ أخطاء ]│
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│                         صفحة الدفتر المختارة                         │
│                                                                      │
│                         محتوى كامل بلا تقسيم                        │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

| البند | القرار |
| --- | --- |
| النتيجة مقابل الكود | صفحة واحدة فقط في مساحة المحتوى. |
| العناصر الثابتة | شريط علوي 48، صف صفحات 48، ومحتوى مرن. |
| التداخل | منخفض جداً؛ لا توجد ترويسة داخلية ولا شريط جانبي ولا `SplitContainer`. |
| الانطباع | أبسط وأسهل لطلاب الفريق عند التشغيل. |

يناسب هذا الخيار إذا أردت واجهة **مضمونة وسهلة** ولا تريد مفاهيم جانبية كثيرة.

## التصميم 4 — Source + Inspector

هذا التصميم الوحيد الذي يبقي الكود والنتيجة معاً، لكنه يمنع التداخل بحاويتين فقط: مصدر عريض في اليمين، ولوحة فاحص ضيقة في اليسار. لوحة الفاحص لا تحتوي تبويبات؛ تحتوي قائمة صغيرة في الأعلى ومحتوى واحداً أسفلها.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ بيان | فتح | حفظ | تحليل وترجمة                                     │
├───────────────────────────────────────┬──────────────────────────────┤
│                                       │ artifact: [ MIPS        v ]  │
│             كود المصدر                ├──────────────────────────────┤
│                                       │                              │
│                                       │      محتوى artifact          │
│                                       │                              │
└───────────────────────────────────────┴──────────────────────────────┘
```

| البند | القرار |
| --- | --- |
| النتيجة مقابل الكود | يظهران معاً دائماً، لكن لكل منهما عمود مستقل فقط. |
| العناصر الثابتة | صف أوامر واحد، وعمودان فقط تحت الصف. |
| التداخل | لا توجد طبقات إضافية؛ `TableLayoutPanel` بعمودين هو كل التخطيط. |
| الانطباع | عملي لمن يكتب الكود ويقارن النتائج بشكل متكرر. |

يناسب هذا الخيار إذا كانت رغبتك الأساسية هي مشاهدة البرنامج وMIPS أو التشخيص في الوقت نفسه.

## المقارنة والقرار

| إذا كانت الأولوية | اختر |
| --- | --- |
| أهدأ واجهة وأقل عناصر | **1 — Studio Canvas** |
| عرض مراحل المترجم أمام الدكتور بلا تداخل | **2 — Compiler Journey** |
| أبسط واجهة للتشغيل داخل الفريق | **3 — Split-Free Notebook** |
| رؤية المصدر والنتيجة معاً | **4 — Source + Inspector** |

لا أوصي بالعودة إلى التخطيط الحالي الذي يجمع أعمدة وتبويبات وشريط مراحل في وقت واحد. اختر رقماً واحداً، وسأعيد بناء النافذة من الصفر بهذا التخطيط فقط، مع الحفاظ على شاشة الترحيب وCLI المستقل والعينات `.bayan`.
