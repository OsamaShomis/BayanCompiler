# تحقق Compiler Journey

## تحقق منفذ في Linux

| الفحص | النتيجة |
| --- | --- |
| بناء `Bayan.Compiler.Core` | نجح. |
| بناء `Bayan.Compiler.Cli` | نجح؛ تحذير `NETSDK1138` فقط لأن `net6.0` خارج الدعم. |
| مجموعة اختبارات LL(1) الرسمية | نجحت **25 من 25**. |
| CLI على `12_official_basic_execution.bayan` | نجح حتى `MIPS` مع `Success = true` و`DiagnosticCount = 0`. |
| وجود artifacts للحل الرسمي | تحقق وجود `program.asm` و`parse-tree.txt` و`symbol-table.txt`. |
| عينة `01_valid_program.bayan` | فشلت بصياغة قديمة، ولذلك صُنفت مؤرشفة وليست عينة قبول رسمية. |

## قيد تحقق Windows Forms

لم يُبنَ `Bayan.Editor.WinForms` في Linux لأن SDK المحلي لا يحتوي `Microsoft.NET.Sdk.WindowsDesktop.targets`. كما لا توجد أداة C# مستقلة أو مرجع `System.Windows.Forms.dll` محلي لإجراء تحقق بديل. لذلك لا يمكن الادعاء بأن الواجهة شُغلت أو فُحصت بصرياً في هذه البيئة.

## قائمة تحقق Windows المطلوبة

نفّذ في Visual Studio 2022 على Windows: **Clean Solution** ثم **Rebuild Solution** ثم تشغيل `Bayan.Editor.WinForms`.

| السيناريو | المتوقع |
| --- | --- |
| بدء التطبيق | شاشة ترحيب أحادية العمود بلا قص أو تداخل. |
| برنامج جديد | انتقال إلى مرحلة المصدر في Compiler Journey. |
| فتح `12_official_basic_execution.bayan` | تحميل المصدر وظهور شارة نجاح. |
| تحليل وترجمة | تعطيل الأوامر وظهور شريط تقدم ثم مرحلة MIPS عند النجاح. |
| المرحلة 02–08 | عرض artifact واحد فقط في كل شاشة، مع انتقال السابق/التالي. |
| اختبار خطأ محرف | انتقال إلى التشخيصات مع شارة خطأ، ومن دون ادعاء توليد MIPS. |
| حجم نافذة صغير ومتوسط وكبير | لا نصوص مقصوصة، ولا أزرار متراكبة، ولا مناطق محتوى متداخلة. |

> عند العثور على خلل بصري أو وظيفي، أرسل لقطة شاشة نافذة التطبيق مع **Output → Build** إن كان الخلل أثناء البناء، ليتم تشخيص السبب الجذري بدلاً من تطبيق تعديل تجميلي غير مؤكد.
