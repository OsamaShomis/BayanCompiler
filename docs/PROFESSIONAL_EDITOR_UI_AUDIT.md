# تدقيق واجهة محرر «بيان» قبل إعادة التصميم

## النتيجة

واجهة `CompilerJourneyForm` الحالية صحيحة وظيفياً في فصل المحتوى؛ فهي تعرض سطحاً مركزياً واحداً عند اختيار أي artifact. إلا أن تجربة الاستخدام تبقى مزدحمة لأن شريط الانتقال السفلي يضم **12 مرحلة متساوية الحجم في صف واحد**، ويضطر المستخدم إلى التمرير الأفقي عند صغر النافذة. كما أن صف الأوامر يمنح فتح وحفظ وترجمة وتنفيذ MIPS وتنفيذ EXE وزر الحفظ وزناً بصرياً قريباً، فلا تظهر الأولوية الحقيقية للترجمة بوضوح.

## ما يجب الحفاظ عليه

| الأصل الوظيفي | سبب الحفاظ عليه |
| --- | --- |
| `CliCompilationClient` | يستدعي المترجم المستقل ويقرأ artifacts الحقيقية. |
| `stageArtifacts` | يحفظ نتائج كل طور من تشغيل CLI نفسه. |
| `MipsRuntimeClient` و`WindowsExecutableRuntimeClient` | يفصلان تشغيل MIPS وEXE عن واجهة العرض. |
| `ShowStage` | يضمن وجود سطح محتوى واحد فقط في المنطقة المركزية. |
| حالات `SetBusy` و`SetStatus` | تمنع عمليات متزامنة وتعرض نص حالة يمكن قراءته. |

## سبب التداخل والمخاطر

| العنصر الحالي | الأثر البصري أو التشغيلي |
| --- | --- |
| 12 زر مرحلة بعرض ثابت `70px` | ازدحام أفقي وتمرير يصعب اكتشافه في النافذة الصغيرة. |
| صف أوامر واحد طويل | قد يقطع الأزرار أو يخفي زر التنفيذ أو زر الحفظ عند تضييق النافذة. |
| مراحل التحليل والهدف والنتيجة متساوية في الشريط | لا يظهر التسلسل الذهني: تحليل ثم تمثيل ثم هدف ثم تنفيذ. |
| عرض أزرار MIPS وEXE جنباً إلى جنب دائماً | يخلط مساري التشغيل في تجربة المستخدم العادية. |

## قرار إعادة التصميم

ستستبدل قائمة المراحل المسطحة بخمس محطات رئيسية: **المصدر، التحليل، التمثيل الوسيط، الأهداف، النتيجة**. عند اختيار محطة تظهر قائمة فرعية صغيرة خاصة بها فقط، مثل `Tokens` و`LL(1)` و`الشجرة` داخل محطة التحليل. لذلك لن يرى المستخدم أكثر من خمسة أزرار رئيسية وعدد محدود من الأزرار الفرعية في لحظة واحدة.

سيصبح صف الأوامر ذا مجموعتين: مجموعة ملف هادئة (`جديد`، `فتح`، `حفظ`) ومجموعة إجراءات تتضمن زر **تحليل وترجمة** الأساسي، بينما توضع إجراءات MIPS وEXE في محطة الأهداف وتفعل فقط عند وجود artifact حقيقي. سيظل التخطيط مبنياً على `TableLayoutPanel` بمناطق حصرية وليس على عناصر `Dock` متنافسة.
